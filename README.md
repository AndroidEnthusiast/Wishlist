# Wishlist (Android)
Kotlin + Jetpack Compose (Material 3). Link parsing with Jsoup, images with Coil, price-drop checks with WorkManager.
Font: Google Sans (SIL OFL, see FONT-LICENSE-OFL.txt).
Build: `gradle assembleDebug` -> app/build/outputs/apk/debug/app-debug.apk

## Online sharing (v2.2)
Free Supabase project plus a static web page on GitHub Pages.
- Run `supabase-setup.sql` once in the Supabase SQL editor. Put the Project URL and publishable key in
  `app/src/main/java/com/wishlist/app/Config.kt` (and at the top of `web/index.html`).
- Upload `web/index.html`, `web/og.png` and `web/icon.png` to the repo root (same names) and turn on GitHub Pages (Settings -> Pages ->
  Deploy from a branch -> main / root). Friends open `https://<user>.github.io/<repo>/?c=CODE`.
- Owner: menu -> Settings -> Sharing (or the share icon) sends that link. No app needed for friends.
- Reservations are only ever fetched by the web page and friends' devices. The owner's app never requests them.
- Without Supabase values the share button falls back to a plain-text export.
- Wishes can be edited (pencil icon on each card). Editing syncs to the shared page.
- Link reading (v2.3): plain request first; if the store blocks it or no price is found, the page is loaded in a hidden in-app browser (Browser.kt). Funda/Etsy-style pages are handled by text and JSON-LD fallbacks in Fetch.kt.
- Views (v2.4): category dropdown + three view buttons (large cards, two per row, images only with price tag). The choice is remembered. In images-only view, tapping a tile opens a detail dialog with Edit / Got it / Remove / Open in store.
- Alerts (v2.5): Alerts.kt holds the schedule, notification and settings shortcuts. Settings -> Price alerts has interval (1/3/6/12/24 h), last check time, Check now, Test notification, and shortcuts to battery/notification settings. Notification: title 'Price drop on your wishlist', text '<item> is now X (was Y, -Z%)'.
- Menu (v2.6): side menu is ~72% of the screen width, the screen behind it blurs (Android 12+), and the menu button is drawn above the menu as an animated hamburger that spins into an X. Screens keep an empty MenuSlot() where the button sits.
- Add/Edit dialog (v2.7): no Paste button; pasting a whole link fills in the details automatically (Fetch details stays as a retry). The link is optional, so custom wishes work. ImageBlock shows a dashed '+ Add image' block that opens the photo picker; the picture is copied into the app (ImageStore.kt, max 1024 px). Pictures chosen this way are not uploaded to Supabase, so friends on the web page see a gift icon for them.
- Photo sharing (v2.8): run `supabase-photos.sql` once. Pictures you add yourself are uploaded as small (600 px) JPEG copies to the public Supabase bucket `wish-photos` under `<code>/<file>.jpg`; only the list owner (secret `x-owner-token` header) can add or delete them. Pictures are removed again when the wish or picture is removed, or when sharing stops. Settings -> Sharing shows the upload status.
- Price history (v2.9): long-press a wish (any of the three views) -> Price history / Share item. History is stored on the phone only (History.kt, SharedPreferences key 'history'), never in Supabase; a point is saved only when the price changes (max 400 per wish). Chart logic is in ChartMath.kt (pure Kotlin, unit-tested), drawing in PriceHistory.kt. Wishes saved before v2.9 start tracking from the first launch of v2.9.
- Friends' page views (web only, no app change): `web/index.html` has the same three view buttons as the app (large cards, two per row, images only). Each visitor's choice is remembered in their own browser (localStorage `wl_view`); it is never sent to Supabase. In images-only view, tapping a picture opens the full card so the gift can still be reserved. Each phone that publishes a list gets its own random code and link on the same page (`?c=<code>`); lists are separate.
- Share text (v2.10): sharing your list sends only the link (no message around it). Wording on the page, in link previews and in `web/og.png` is "so nobody gives the same gift twice".
- Categories (v2.11, chip alignment fixed in v2.12): Add/Edit wish dialog has a "New" chip; the category you create there is selected for that wish right away. Long press a category (chip in the wish dialog, row in the home drop-down) -> Edit (rename; its wishes move along) or Delete (wishes stay, without a category). Settings -> Categories has the same edit/delete buttons. Code: `Categories.kt`, `Repo.addCat/renameCat/removeCat` in `Data.kt`. Names are unique ignoring capitals; "All" is reserved.
- Helping givers choose (v2.13): (1) Most wanted: `Wish.star`. Gold label with a star in the top right of the picture (star only on small cards and tiles). Owner: tap the outlined star on a large card's picture, or use the menu (compact card), the star button (detail dialog), the long-press menu, or the switch in Add/Edit. Wishes you already got show no star. Code: `MostWanted.kt`. (2) Notes: `Wish.note` ("Note for givers" in Add/Edit, shown on cards and on the web page) and a note for the whole list (Settings -> Note for friends, `Repo.about`, max 300 characters). The list note is sent as one extra item with id 0 and kind "about" (no Supabase change needed); the web page and `Cloud.fetchList` take it out of the wishes. (3) App: search icon in the top bar (title, description, note, category, shop name) and a Sort button (newest, most wanted, price low/high, name); the sort is remembered. Logic and tests: `Sorting.kt`, UI: `Browse.kt`. (4) Friends' page: gold star label, notes, a 'Good to know' box, and a Sort & filter panel (most wanted first / as listed / price, max price, only gifts still available). The sort is remembered in the visitor's browser, the filters are not.
- Feedback round (v2.14): (1) The "Most wanted" label has a small cross (✕) when you can tap it to remove it (owner view only; friends see the plain label). (2) The Sort button moved out of the view buttons: it sits right of the category drop-down; when a sort is active it is highlighted and shows its short name (`sortShortName` in `Sorting.kt`). (3) Sizes are picked, never typed: `Wish.size` is one of `SIZES` (XS, S, M, L, XL) chosen in a drop-down in Add/Edit ("No size" clears it; `SizeField` in `Sizes.kt`). Shown as a small "Size M" tag on cards, in the detail dialog and on the friends' page (`.sizetag`, text only). The note field no longer mentions sizes. No Supabase change: the size travels inside each wish's JSON.
- Shared wishlists (v2.15, step 1 of collaboration): run `supabase-shared.sql` once in Supabase (after the two earlier scripts). A shared list is a normal row in `wl_lists` (so the friends page `?c=CODE` and reservations work unchanged) with an extra secret `edit_key`. The invite link is `<page>/?j=<edit key>`; whoever has the key can add, change and delete wishes, one wish at a time (`wl_sh_put_item`, `wl_sh_del_item`, and since 2.16 the small name/note/category functions, see the next bullet), so two people never overwrite each other's whole list. Editors never get reservations. The phone that created the list also keeps the owner token: only that one can make a new invite link (`wl_sh_reset_key`) or delete the list. Pictures: editors upload with the header `x-edit-key` (`wl_owner_ok` accepts it). In the app: hamburger menu -> My wishlist, a line, "Shared wishlists" (the lists, then a line, then New shared wishlist; the manual "Join with a link" entry was removed in 2.17). Code: `Shared.kt` (state, saving, refresh every 20 s while open, undo when saving fails), `SharedUi.kt` (new/join/share dialogs), `Repo.wishes/cats/listName/about` now follow the list that is open, while `Repo.myWishes` etc. are always My wishlist (used by `Sync` and `PriceWorker`). Invites open via the share sheet, the clipboard after an install (2.17), or `wishlist://join?j=KEY`. The web page shows an invitation page for `?j=KEY` (editing in the browser came in v2.20). Not yet: price-drop checks for shared lists.
- APK download for invited people (web + workflow, app unchanged): the invite page has "Open in the app" and "Download app". Download app is a plain link to `https://github.com/AndroidEnthusiast/Wishlist/releases/download/latest/Wishlist.apk`, which GitHub redirects straight to the file, so the download starts at once without a GitHub page or login. The release (tag `latest`, one file `Wishlist.apk`) is made by the ONE workflow `.github/workflows/build.yml`: its step "Publish APK to Releases" runs after every successful build, deletes the old `latest` release and creates a new one with the fresh APK (same fixed signing key, so it updates over an installed app). The same workflow's `pages` job deploys `web/`. There is no second workflow. Workflow files must be edited on GitHub itself; a workflow file inside the zip is not picked up. If a `release-apk.yml` file or a release called `apk-latest` still exists from an earlier version of these notes, delete them.
- Editing together without losing work (v2.16): run `supabase-shared.sql` again (completely; it is safe to repeat and upgrades the earlier version). (1) Saving a wish sends only the fields that were changed (`Shared.changedFields`, compared with the version the edit form started from; quick buttons like the star compare with the current wish) and `wl_sh_put_item(p_key, p_item, p_fields)` writes just those fields on top of what is online (a field missing from the wish is cleared; the wish row is locked while merging; a wish deleted meanwhile is stored again whole). So one person changing the price and another the note both stay. Same field at the same moment: the later save wins. (2) The list name, the note for friends and every category change are separate steps online (`wl_sh_set_name`, `wl_sh_set_about`, `wl_sh_cat_add`, `wl_sh_cat_rename`, `wl_sh_cat_remove`); renaming or removing a category also moves wishes someone else added a second ago. `wl_sh_set_meta` stays for older apps. (3) After a good save the app asks the online copy again (so merged changes show at once), and a refresh that started before a local change is ignored (`stamp`), so a new wish can't flicker away. (4) A picture is only deleted online by the person who replaced it in that save, never because of an out-of-date screen. Still by design: no internet = the change is undone with a message (online-first). Tests run here: 12 two-phone scenarios (`Shared.kt` with a fake server, before: 9 failed, after: all pass), the 52 earlier shared-list checks, and the SQL on a real Postgres 16 (merge, clearing, categories, wrong keys, upgrade from the old function, two sessions at the same moment, 18 parallel changes). A new field on `Wish` must be added to `wishToJson`, `wishFromJson`, `changedFields` and `applyFields`.
- Joining, menu and dialogs (v2.17, app + web page, no SQL): (1) Menu: My wishlist | line | Shared wishlists (the lists) | line | New shared wishlist. "Join with a link" is gone; `JoinDialog(key, ...)` only appears for an invitation that arrives by itself (opened `wishlist://join?j=KEY`, a link shared into the app, or the clipboard) and checks it at once (Try again when offline). (2) Install from the invite page: Android passes nothing through a sideloaded install, so the page's "Download app" button copies the invite link (`copyText`: clipboard API, else `execCommand('copy')`; failing never blocks the download) and shows "Invitation copied...". The first time the app gets window focus after an install or update (`MainActivity.checkClipboardInvite`, remembered per `lastUpdateTime` in pref `inv_clip_for`, so it reads the clipboard once per install) it looks for a link with `J=KEY` (`Shared.inviteFromClipboard`: needs a real link, not a bare key; not for a list this phone is already on), clears the clipboard, and opens the Join screen (asks for the name). An invitation that came in as a link/shared text wins over the clipboard. Android 12+ may briefly show "Wishlist pasted from your clipboard". If the clipboard was overwritten in between, the page's "Open in the app" still works. (3) The Add/Edit wish, New shared wishlist and Join dialogs ignore taps outside (`DialogProperties(dismissOnClickOutside = false)`); only Save/Cancel/Join or the Back button close them. Tests here: 16 clipboard-logic checks (real `Sync.parseInvite` + `Shared.inviteFromClipboard`), 133 page checks (clipboard copy, both fallbacks, failure, hostile list names), the 12 two-phone and 52 shared-list scenarios again. The Compose screens are only compiled by GitHub.
- Careful deleting and "Save to" (v2.18, app only, no SQL): (1) Every wish Delete button (card icon, long-press menu, detail dialog; labels now say Delete) calls `DeleteFlow.request` (`Delete.kt`; the question and the Undo message are `DeleteHost` in `DeleteUi.kt`, placed once in `App`). Default: "Delete this wish?" with Cancel. Settings -> "Deleting wishes" -> "Instant delete" (pref `instant_delete`, `Repo.instantDelete`, default off) skips the question. Both ways a snackbar "Deleted ... Undo" shows for 10 s. (2) Undo is real: the wish leaves the screen at once, but what belongs to it stays until the time is over (`Repo.trash/untrash/finishTrash` for My wishlist, `Shared.trash/untrash/finishTrash` for shared lists, `Trashed` in `Trash.kt`): the online copy and a friend's reservation on it (My wishlist keeps the wish in what `Sync` pushes via `Repo.syncWishes()`; a shared list keeps it online and hides it from refreshes via `hidden`), the picture, and the price history. Only the latest delete can be undone; a next delete, leaving the app (`MainActivity.onStop`, not for a screen turn) or the 10 s ending makes it final. If the final online delete fails (no internet) the wish comes back with a message. If the app is killed in that time the wish is simply still online (shared) or gone locally with an online copy that disappears at the next push (My wishlist). `Repo.remove` was removed on purpose: nothing can delete a wish without the flow. (3) Sharing a link into the app from the browser opens the Add dialog with a "Save to" drop-down (`SaveToField` in `SaveTo.kt`) when there is more than one wishlist: My wishlist and every shared list (`saveTargets()`; when own extra lists are built later, list them there). Choosing one opens that list (so its categories show), Cancel goes back to the list that was open, Save leaves you in the list it was saved to. The normal + button has no chooser (you add to the list you are in). Tests here: 41 scenarios for delete/undo/My wishlist/Save-to with the real `Shared.kt`, `DeleteFlow` and the real trash code from `Data.kt` (checked by breaking the code on purpose in three ways: all caught), plus all earlier suites (12 + 16 + 52) again. Compose screens are only compiled by GitHub.
- Star effect (v2.19, app only, no SQL): marking a wish as most wanted plays a short pulse of the star and seven tiny sparkles (thin darker edge so they show on gold, white and dark pictures; about 0.65 s). Only a tap plays it: a card scrolling into view, a refresh from another phone or switching a wish off never does. Two-per-row view: the owner now always gets a round star on the picture, 34 dp, no text because there is no room: outlined on a dark circle when not most wanted, solid on gold when it is (`CompactCard(onStar = ...)`); tap again to switch it off. Friends and wishes you already got show no button. The images-only tiles keep the plain star. The menu entries ("Most wanted") do not play the effect because the menu closes at once. Checked here: MostWanted.kt type-checked with hand-written stand-ins for the Compose libraries, bracket check and syntax scan of all files, and the sparkle motion drawn frame by frame on light and dark backgrounds; how it feels on screen can only be judged on the phone.

## Editing in the browser (v2.20, web only + one helper function, no SQL, app unchanged)
People without an Android phone (iPhone, iPad, a computer) can edit a shared list in the browser, with the same rules as the app.
- Where: the invite link `<page>/?j=KEY` still opens `index.html`. On an Android phone it shows "Open in the app", "Download app" and "Edit in the browser". On anything else it goes straight to `edit.html?j=KEY` (`isAndroid()` / `editorUrl()` in `index.html`). The editor works on any phone or computer and can be added to the home screen.
- Files (all in `web/`): `edit.html`, `edit.js`, `edit.css` (the editor), `parse.js` (reads a product page; a port of `Fetch.kt`: if you change one, change the other), `wishlist.css` (styles shared by `index.html` and `edit.html`, moved out of `index.html`). `supabase/functions/fetch-page/index.ts` is the helper function (below). Nothing is needed from Supabase beyond `supabase-setup.sql`, `supabase-photos.sql` and `supabase-shared.sql` that the app already uses (the same `wl_sh_*` functions and the `wish-photos` bucket with the `x-edit-key` header).
- What it can do (same as the app for an invited editor): see all wishes in the three views (large, two per row, images only), category chips, search, sort (newest, most wanted, price low/high, A-Z), add a wish by pasting a link (title, picture, description and price are filled in), add or edit by hand, choose a picture (shrunk to 600 px JPEG and uploaded like the app does), size, note for givers, most wanted (star pulse and sparkles, also in the two-per-row view), got it, delete with a question, 10 seconds of Undo and the "Instant delete" setting, categories (add, rename, delete, "New" inside the wish form), rename the list, the note for friends, the share dialog (invite link and friends' link), "Your name" (shown as "Added by"). Not in the browser, on purpose: making a new invite link and deleting the whole list (only the phone that created the list can), price-drop checks, reservations (editors never see them).
- Working together: the same rules as `Shared.kt`. A change shows at once and is saved in the background, field by field (`changedFields` / `applyFields` in `edit.js`; one person changing the price and another the note both stay). If saving fails the change is undone with a message. The list refreshes every 20 s, when the tab is shown again and when the internet returns; an old answer is ignored when you changed something meanwhile (`stamp`). A deleted wish is removed online only when the Undo time is over (or when the page closes), and its picture goes with it. A new field on `Wish` must be added to `normWish`, `wishJson` and `FIELDS` in `edit.js` as well as in the app.
- Reading a shop link: a web page may not load another site's page, so the editor asks the helper function `fetch-page` for the page's HTML and reads it itself with `parse.js`. The function only answers people who hold a valid invite key, only loads public addresses (no localhost or private networks, every redirect is checked again, ports 80/443, 1.5 MB, 12 s). One-time setup: Supabase dashboard -> Edge Functions -> Deploy a new function -> Via Editor -> name it exactly `fetch-page` -> paste `supabase/functions/fetch-page/index.ts` -> Deploy -> open the function and switch OFF "Verify JWT" (the key is checked inside the function; the built-in check only understands the older kind of key). Without the function the editor still works: "Couldn't read that page. Fill in the details yourself." Some shops (Amazon, for example) refuse requests from data centres: then the message says the shop blocked it and you type the details.
- Tests run here (they now live in `tests/`: `cd tests && npm install && npx playwright install chromium && bash run-all.sh`; see `tests/README.md`; the standing rules for Claude Code are in `CLAUDE.md` and the history in `docs/HANDOFF.md`). The app itself is only compiled by GitHub: 54 checks for `parse.js` against the Kotlin logic (prices, currencies, Amazon, JSON-LD, Funda, blocked pages), 100 checks for the helper function in real Deno (private addresses, redirects, size and time limits, wrong keys), 170 browser checks for the editor in Chromium against a pretend Supabase (viewing, the three views, adding by link and by hand, editing one field, star effect, got, delete/Undo/instant delete, categories, list name and note, share dialog, failed saves, sorting and search, offline copy, picture upload/replace/remove and failed uploads, two people at once, an old refresh answer, the iPhone tip, name change), 8 checks for the invite page and the friends' page in the browser, and 140 checks for `index.html` in jsdom (133 earlier plus the new invite behaviour).
- Could not be checked here: the real Supabase (the picture upload sends the headers `x-edit-key` and `cache-control` from another website: if the browser refuses, the wish is saved without the picture and says so), whether the helper function is deployed, what a given shop answers, and how it looks on a real iPhone (Safari). If a picture upload fails in a real browser, the Supabase storage CORS settings are the first place to look.
